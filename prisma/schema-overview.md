# Schema Overview

This schema models interactive troubleshooting flows as **directed graphs**. Each flow is scoped to a specific issue category (e.g. "ikke-på-nett") and a specific device type (e.g. "Huawei B818").

---

## The flow graph model

Each **Article** represents one complete troubleshooting flow. The flow is a directed graph where:

- **Step** = a node. It presents a question or instruction to the user.
- **StepChoice** = a directed edge. It represents one selectable answer from a step, pointing to the next step (or ending the flow).

A user starts at a root `Step` in the article, reads the content, selects a `StepChoice`, then moves to `StepChoice.nextStepId` — and so on until the flow ends.

```
Article
  └── Step (root)
        ├── StepChoice → Step → StepChoice → Step → ...
        ├── StepChoice → Step → StepChoice (terminal)
        └── StepChoice (terminal)
```

A `StepChoice` is **terminal** when `isTerminal = true` and `nextStepId = null`. Terminal choices end the flow. The `terminalReason` enum records why:

| TerminalReason | Meaning |
|---|---|
| `EXTERNAL_REDIRECT` | User is sent to an external URL |
| `FLOW_EXIT_EXPECTED_SPEED` | Flow ends because speed is within expected range (For the yes awnsers on the speedtest pages where the question is do you have the expected speed) |
| `FLOW_EXIT_NO_NEXT_STEP` | Flow ends with no further step available |
| `FILTERED_CROSS_FLOW` | Choice filtered out — would have crossed into another flow |

`StepChoice.sortOrder` controls display order. `@@unique([stepId, sortOrder])` enforces no duplicates per step.

## Organizing flows

```
Category ──< Article >── DeviceType
               │
               └──< Step >──< StepChoice
```

- **Category**: Issue area (slug, e.g. `ikke-pa-nett`).
- **DeviceType**: Router/device family (slug, e.g. `huawei-b818`).
- **Article**: The entry point for a flow. Has a unique `slug` and belongs to exactly one `Category` and one `DeviceType`.

---

## Session tracking

A **TroubleshootingSession** is created when a customer service representative enters a `sessionCode` to look up a user's session. As the representative steps through the flow on behalf of the user, each answered step is stored as a **SessionStepAnswer**:

```
TroubleshootingSession
  └── SessionStepAnswer (one per step visited)
        ├── step      → Step
        └── choice    → StepChoice (or null if free-text answer)
```

- `sessionCode` is a unique, stateless encoded string provided by the application (not auto-generated by the DB).
- `customerId` optionally links the session to a `User` (the customer). If the user is deleted, the session is kept but `customerId` is set to `null`.
- `SessionOutcome` tracks lifecycle: `IN_PROGRESS → RESOLVED | ESCALATED | ABANDONED`.
- `@@unique([sessionId, stepId])` ensures each step is only answered once per session.

## Localization

`Step.title`, `Step.content`, `Step.agentNote`, `StepChoice.label`, and `StepChoice.buttonText` all store **localization keys**, not raw display text. These are resolved at render time from locale JSON files under `telenor-kb/public/locales/`.

Example key: `ikke-pa-nett.huawei_b818.step_check_lights.title`
